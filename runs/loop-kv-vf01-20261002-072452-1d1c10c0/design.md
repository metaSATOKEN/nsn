# LOOP-KV-VF01：V復元をattentionへ組み込む部品比較

2026-10-02 / v0.1 / 設計段階。ユーザーの「予定通り次に進もう、まずは設計」に対応する。実装・Colab実測は次工程。

## まず何を確かめるか

**圧縮されたVをいったん全部書き戻す代わりに、attentionが使う小区画だけ復元すれば、数値と異常検出を保って時間や一時メモリを減らせるか。** 今の処理、新しい復元計算、融合の効果を3方式で分けて調べる。

AC06では、未使用4冊でも品質への影響は小さく、検査集約の時間短縮が残った。一方、同runの非量子化よりdecode時間は12.849%長かった。今回は、その残差をすべてVの費用と仮定せず、V復元を含む部品を同じ入力から測る。

モデルを新たに回す必要はない。AC06の局所保存物には復元済みVしかないが、**RF01には圧縮Kと圧縮Vの両方が、同じ軌道・時点・slotで保存されている**。この18ファイルを9組の入力として再利用する。queryはQK01と同じ固定合成4種。今回の答えは部品の数値・時間・メモリまでで、PPLと推論全体の速度は、その後のモデル接続で測る。

## 1. 3方式と比較の意味

| 方式 | Vの扱い | 共通のattention | 見たい差 |
|---|---|---|---|
| RF01_MATERIALIZE（現行基準） | 実完走RF01の復元、BF16化、tail連結でV全体を作る | 現行AF01のK復元・QK・softmax・加重和 | 現行部品の基準 |
| TILE_MATERIALIZE（橋渡し対照） | 候補と同じ区画単位の復元計算で、BF16 V全体を作る | 同じAF01 | norm計算等の実装差 |
| V_FUSED（融合候補） | 区画内でVを復元してBF16へ丸め、直ちに加重和へ使う。V全体は書き出さない | AF01のpartialへV復元を加え、mergeを再利用 | V全体の書出し・再読出し・tail連結等を省く効果 |

主速度比は **V_FUSED / TILE_MATERIALIZE**。実装全体としての副速度比 **V_FUSED / RF01_MATERIALIZE**、復元実装差 **TILE_MATERIALIZE / RF01_MATERIALIZE** も必ず併記する。橋渡し対照より速いだけでは、現行より速いとは言わない。

変更するのはV復元を置く場所と、そのために必要な接続・検査である。K側の式、softmax、tile統合、入力、圧縮率、保存形式は固定する。時間差はkernel起動や検査の回収方法も含む処理方式の差であり、メモリ帯域だけの効果には分解しない。

## 2. 使う入力と規模

[固定入力・全計時予定](loop-kv-vf01-input-contract-v0.1-2026-10-02.json)に、原NPZごとのhash、元cache digest、query hash、比較順を記録した。

| 入力の由来 | 組数 | 全長 / 圧縮済み / tail |
|---|---:|---|
| RF01既知2冊（3752 / 31131）×slot 0 / 95 / 191 | 主6組 | 1,023 / 896 / 127 token |
| RF01先行1冊（37013）×同3slot | 診断3組 | 833 / 768 / 65 token |

各組のK/Vは同じ軌道・時点・slotで対応させる。16head、head次元128、batch1、1 query、全保存位置参照、scale=1/sqrt(128)、dropoutなし、GQA・任意maskなし。slotは独立文章や独立モデルではない。

4 queryは標準正規・head別one-hot・交互符号±1・全ゼロ。既存QK01関数とseed `2026100104 + 組番号` をそのまま使う。9組×4 query＝36条件。**主6組の非ゼロ3queryを速度の主集計**にし、全ゼロと先行3組は別表にする。ゼロqueryでもattention出力は通常ゼロではなくVの一様平均になる。

原ZIPのSHA256は `79a9bfda5e8e0280188827b4003b88b8844934e5d700eb7ac1bce1f9cd4f9f7c`。18 NPZは計66,043,379 bytes（約63.0 MiB）。元header・shape・dtype・有限性・参照とcache digestの対応を手元で照合済み。再量子化・K/Vの別時点接ぎ合わせ・成績による標本選別は行わない。

## 3. 復元式と実装を固定する

候補のV復元は、既存QK01/AF01でK側に使う処理をVへ移植する。3bit整数を読み、FP32で `d = m + s × code`、`den = max(sqrt(sum(d²)), 1e-12)`、`v = n × (d / den)` とし、n=0では0を選ぶ。**加重和に掛ける前にBF16最近接偶数丸め**を行い、その値をFP32へ戻して使う。norm係数を内積の後へ移したり、BF16丸めを省いたりしない。

RF01基準はPyTorch vector_norm、候補はTritonの区画内reductionである。演算順の差が生じ得るので、RF01とのbit一致を事前の事実にはしない。橋渡し対照と融合候補では、同じV復元helperを用いる。token tile16、4warps、FMA無効、div_rn、FP32部分統計、既存AF01の2段統合を固定。autotuneや結果を見たtile変更は行わない。

V_FUSEDの通常経路は全長V・全長score・確率行列を生成しない。TRACEだけで候補Vとscoreを保存し、通常出力との対応を照合する。診断用bufferを計時へ持ち込まない。全長FP32方向配列やeffective_normを常設する方式は今回追加しない。

## 4. 数値は三段で確かめる

### 4.1 経路の一致

同じGPUでRF01基準Vを復元する。RF01原保存のBF16参照との差も別に残し、過去値を上書きしない。凍結RF01経路の直接呼出しと新wrapper、旧AF01直接呼出しと現行基準wrapperの出力は一致必須とする。

K側を変えていない確認として、3方式のTRACE scoreはbit一致を要求する。TILE_MATERIALIZEとV_FUSEDの復元BF16 V、FP32 context、最終BF16出力もbit一致を要求する。各方式のTRACE/通常出力一致、計時初回・区間末尾の再現、入力不変も検査する。有限不一致は原値を残し、経路一致未達として扱う。

### 4.2 V復元の差

同じGPUで得たRF01基準Vと候補Vを比較する。K側に使用した既存工程予算を、V側の新しい適用として取得前に固定する。

- 各token：最大絶対差 ≤ `1e-6 + 2^-7 × max(abs(V_ref))`。
- 各head：RMSE ≤ `1e-6 + 2^-8 × RMS(V_ref)`。

bit不一致数・最大差・RMSE・予算外token/head数を残す。これはBF16復元の工学的な基準であり、PPL5%基準の代用ではない。

### 4.3 attentionの差

各TRACE scoreにNumPy FP64 softmaxを適用し、pを求める。方式自身が使ったBF16 VでFP64加重和を再計算し、FP32 contextを既存AF01予算 `2e-6 + 2e-6 × sum(abs(p × V))` へ照合する。

さらに、同じscoreとRF01基準Vを使う参照に対して、context全体の差を点検する。候補自身の積和尺度をA、V復元差の寄与を `B = sum(p × abs(V_candidate − V_ref))` とし、要素ごとの合成予算を `2e-6 + 2e-6 × A + B` とする。Bの値も保存し、§4.2の復元予算を別に満たすことを必須とする。この分解は、悪い復元を大きなBで無条件に通すためには使わない。

K/scoreの既存QK01予算は維持する。元BF16 K・VとqueryによるFP64 attention全体参照との差、RF01_MATERIALIZEとの最終BF16差も記述する。出力の正しいBF16丸めを別に確認する。工程予算内であることをモデル全体の同値性と読み替えない。

## 5. 入力・異常検査

全方式で、packed K/Vのshape、dtype、device、連続性、header位置・bit数、全長の対応を検査する。query、K/Vのmetadata、両tailは共通の集約有限性検査を**各呼出し内**で行う。既存IV01をコピーし、Vのmetadata/tailを対象へ追加する。全長Vを生成する2方式では復元後の即時検査を維持する。融合候補は方向・norm・復元V・部分加重和・出力の異常flagを戻し、結果を返す前に同じ呼出しで確認する。異常値を無言でゼロ化しない。

headerの内容照合と元hashはGPU転送前に行い、計時中は同じ検証済み不変bufferを使う。毎呼出しの形状・有限性と計時前後の全hashを分けて記録する。

正常16 fixture：圧縮/tailの3形状 `(64,65)、(768,833)、(896,1023)` ×4 pattern（ゼロ、定数、3bit符号混在、部分的なnormゼロ）＝12、tailのみ4長さ17/65/833/1023。各3方式、48出力。ゼロ・定数は解析解、一様重みはFP64平均にも照合する。3bit byte境界、圧縮/tail境界、最終不完全tileを含む。

異常24 fixture×3方式＝72判定。NaN/Inf（query、K/V metadata、tail）、normゼロでも隠してはいけないNaN、dtype・shape・非連続、packed欠損、K/V全長不一致、K/V header位置違反、空入力、有限入力からのscore overflowを固定リストで試す。V normのNaNは最後の圧縮行、V tailのInfは最後のtail行に置く。通常の誤入力は本体起動前に拒否、score overflowは本体内の異常flagで出力を返す前に拒否する。どこで拒否したかも保存する。

旧実装の受理/拒否範囲と変更後の検査対象を、実装時のcoverage表へ対応づける。CPU・模擬検査だけでGPUの異常検出成立とはしない。

## 6. 計時とメモリ

全36条件×3方式＝108セルを最初に1回ずつ実行し、初回時間を分離する。その後全セル各5回、計540 warmupを済ませ、全形状・全方式の準備完了を記録する。主は5round×36条件×3方式＝**540区間、各20回＝10,800呼出し**。方式順は条件番号＋roundで循環し、全予定をJSONで固定した。

計時は圧縮K/VがGPU上にある所からattention出力の即時検査まで。V復元、必要な連結、入力・中間・出力検査、部分統計統合を含む。転送、モデル、投影、RoPE、量子化・cache更新、TRACE、CPU採点、保存は外側。全方式に同じpacked入力の検査を追加するため、RF01_MATERIALIZEの時間もAC06の既報時間そのものではない。

CUDA Eventと同期wallを併記する。専用の空Triton cacheを使い、診断も準備も全て終えた後にsnapshotを固定する。主計時でcacheが変わった場合は時間を残し、`TIMING_CACHE_CHANGED` として準備済み速度の解釈を保留する。追加warmup・良い値までの再測定は行わない。

GPUには共通のpacked K/V・tail・queryだけを常駐させ、基準の全長BF16 VやTRACE配列は計時前に解放する。方式を変えるたびに前の出力を解放し、同じ常駐入力量を確認する。各区間のallocated/reserved基準値・peak・差分、実入力storage、出力storageを記録する。reservedはallocatorの履歴を含む補助指標とし、主メモリ指標は `max_memory_allocated − allocated_before`。必要な中間が減っても、測定peakが減るとは事前に決めない。

各条件・方式の5round中央値から対応比を計算する。主6組では非ゼロ3query比の中央値を組の代表値とし、6組の中央値・範囲・短縮組数を報告する。2冊別・3slot別も併記。p値・CIなし。10,800呼出し、query、slotを独立材料数へ加えない。

## 7. 予想・閉じ方・次の一歩

| 取得前予想 | 判定 |
|---|---|
| H1：経路・入力不変・異常拒否が成立 | §4.1の一致、全予定集合、正常/異常fixtureを照合 |
| H2：候補Vとattentionは工程予算内 | §4.2〜4.3、既存K/score予算を別々に全条件で判定 |
| H3：融合は橋渡し対照より短時間 | 主6組の代表比中央値がCUDA・wall双方で1未満 |

現行RF01基準超え、短縮率、一時peak低下は予測を固定しない。副比較として必ず出す。

全予定がそろった状態は `COMPLETE_COMPARISON`。経路一致、数値予算、異常拒否、計時準備、速度、メモリを別欄にする。有限の予算超過や減速でもrawを保存して予定を終え、後から成功へ補正しない。正常入力で非有限が出た場合は当該条件を記録して安全に他条件を進められる範囲で続けるが、欠測を含む最終状態は `INCONCLUSIVE`。CUDA/OOM、破損入力、版不整合、timeoutは部分保存して停止する。

この固定比較は結果の符号にかかわらず閉じる。経路・数値・異常検出・計時が成立すれば、次は実query・モデル全体のPPL/時間/メモリを確かめる短い接続設計へ進む。部品の短縮率をモデル時間へ掛け算しない。未達なら同じrawを診断し、基準やtileを変えた再試験は別版で固定する。

## 8. 実装時の再利用と配布案

- AF01の実完走partial/merge、計時・全形状warmup・独立NumPy照合をコピーする。
- QK01の入力検証・合成query・Vへ転用する復元式と誤差尺度を再利用する。
- RF01の現行復元を凍結対照とする。旧ファイルを上書きせず、新VF01から呼ぶ。
- IV01の実完走集約検査をV metadata/tailへ差分拡張する。
- 環境とZIP回収は実完走AC06（AC05修復を継承）を基準にし、ID・上限・モデル/HF処理が不要となる部分だけ変更する。GPUライブラリ環境保持、pipなしvenvへの固定版導入を維持する。

Colab GPUの全文1セル、Driveなし、HF_TOKEN不要、モデル/本文の取得なし、終了時ZIP自動DL。入力は18 NPZだけを入れた小さな材料ZIPをコードと一緒に配布する案。ユーザーはこれを `/content` へ配置し、セルを丸ごと実行する。前回の数GBのAC06 ZIPや生きたランタイムに依存しない。材料ZIPがなければファイル選択へ進み、別資料や再量子化で代替しない。

CPython3.13/Linux x86_64、torch2.11.0+cu128、Triton3.6.0、NumPy2.1.3、GPUのBF16対応。実完走AC06の9 package固定環境を再利用する。通常のpackage取得は準備時間へ含める。

提案上限：準備30分＋実験20分、各条件/fixture120秒、worker照合/別process照合/ZIP各120秒、外側60分、成果物1 GiB。入力選択の人間待ちは計算開始前。これは所要時間の予測ではなく上限。新有料サービス・課金APIは使わず、Colabの手持ちruntimeを使用する。

raw packed入力、query、参照/候補V、score/context/output、全計時、fixture、前後hash、環境、失敗、コード・計画のhashを保存する。外側の別process検証器で予定と数値・時間を再計算してからZIPを回収する。元18ファイル以外のRF01原ZIP全部は複製しない。
