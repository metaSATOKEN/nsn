# VF01結果：V復元をattentionへ融合し、部品時間と一時メモリが減った

2026-10-02 / v0.1

**比較は完走し、配布前のNumPy検証器による独立再計算も一致した。融合候補の部品時間は現行基準より41.721%、同じ復元計算を使う橋渡し対照より28.280%短かった。** 一時allocated増分も20.055 MiBから0.526 MiBへ減った。数値は取得前の工程予算内だった。

一方、非連続入力を作るテスト側に不備があり、異常拒否の1種類×3方式は検査器へ到達していない。**H2（数値）・H3（短縮）は成立、H1は未達のまま保持する。** この1種類の確認後にモデル接続へ進むのが次の推奨である。

## 1. 何がそろったか

原状態は `COMPLETE_COMPARISON`、手元の再計算は `OFFLINE_VERIFIED`。全803ファイル・802hash・配布前23埋込sourceが一致した。ZIP内のPythonは実行せず、hashを配布前記録へ照合したローカル検証器を用い、原保存物不変も再確認した。

原ZIPは `loop-kv-vf01-20261002-072452-1d1c10c0.zip`、702,344,412 bytes、SHA256 `0938bfbe0bbb5bc4f0e162dd4addc6568d8bd1333e0108dbf30754e605972e1d`。RTX PRO 6000 Blackwell Server Edition、torch2.11.0+cu128、Triton3.6.0、NumPy2.1.3、CUDA12.8。worker記録は82.509秒で、環境構築・ZIP作成・ダウンロードを含まない。

36条件×3方式の初回108呼出し、540warmup、540区間×20＝10,800計時呼出しを回収した。全形状準備後のTriton cache504ファイルは不変。共通常駐入力は144storage・22,287,360 bytes、GPU入力の前後hashも一致。各方式の初回・5round終端・TRACE／通常の出力は一致した。

正常16例×3方式の48出力がそろい、経路と数値を確認した。異常24種類は各3方式の記録がそろっているが、うち1種類はテストの構成自体が未成立だった。完走状態と、すべての検査目的の達成を分けて報告する。

## 2. 速度：同じ復元計算どうしでも短縮が残った

主は既知2冊×3slotの6組、各組の非ゼロ3合成query。各query・方式で5round中央値を求め、対応比を先に計算して組の代表値にし、6組を集計した。全ゼロqueryと先行3組は[詳細JSON](../data/validation/vf01/analysis.json)へ別に残した。以下の範囲は6組の最小〜最大でありCIではない。

## 3. 数値：復元実装の微小差はあるが、融合による追加の差はなかった

正常16例と保存入力36条件の計52条件すべてで、3方式のscore、橋渡し／融合のV・FP32 context・最終BF16出力、TRACE／通常、現行基準の直接呼出し／wrapperの一致を確認した。正常48出力と保存入力108出力で、V復元・score・context・合成contextの予算を満たした。

| 比較・指標 | 保存入力での値 |
|---|---:|
| 候補VとRF01基準Vのbit不一致 | 108 / 17,688,576要素（9組、query重複を除く） |
| V復元差の最大絶対値 | 0.0078125 |
| 各方式のcontextと自身のVを使うFP64参照の最大差 | 2.457906e−7 |
| 候補contextとRF01基準Vを使う参照の最大差 | 4.076868e−5、固定の合成予算内 |
| 候補BF16出力とRF01基準出力のbit不一致 | 5 / 73,728要素（36条件） |
| 最終BF16出力差の最大絶対値 | 3.051758e−5 |
| 橋渡し対照と融合候補のV・context・出力差 | 全条件0 |

5要素の出力差は先行s191のzero、主b3752/s95のone_hot、主b3752/s191のone_hotとzeroで発生した。橋渡し対照にも同じ差があるため、今回の差は復元実装を替えた段階で生じ、attention内へ組み込む段階では増えていない。RF01と候補ではnormの計算順が異なる。各工程予算と元BF16入力によるFP64 attention差を別に保存した。

この部品実験ではPPLを測っていない。数値予算内であることと、実queryを使うモデル全体の品質は次の接続で対応づける。

## 4. メモリ：一時領域の削減も実測に現れた

主6組・全query・全roundで下記の値は方式ごとに一定だった。主指標は呼出し直前を引いたallocated増分である。

| 方式 | allocated増分（bytes / MiB） | 呼出し中allocated peak（bytes） |
|---|---:|---:|
| 現行RF01基準 | 21,028,864 / 20.0547 | 43,322,368 |
| 橋渡し対照 | 14,665,728 / 13.9863 | 36,959,232 |
| V融合 | 551,424 / 0.5259 | 22,844,928 |

融合の一時増分は現行比97.378%減、橋渡し比96.240%減。共通常駐入力を含む呼出し中allocated peakは現行比47.268%減だった。全方式の直前allocatedは22,293,504 bytes。reserved peakは全方式46,137,344 bytes（44 MiB）で同じだった。

これは保存済みK/Vを使う部品の一時領域であり、モデル全体のVRAMや実packed cache容量の追加削減率とは分ける。V全体を書き戻す中間処理を省いた方式で、今回の測定peakも低下した、という結果である。

## 5. 未達1種類は、非連続入力の作成側にあった

23種類×3方式の69判定は予定どおりの段階で拒否された。残る `v_tail_noncontiguous` の3方式は、`rejected=true` でも予定の `structural` 段階へ到達せず、`cpu_structure / ContractError / input_unchanged=false` と記録されていた。

凍結workerでは、入力をGPUへ置いた後、V tailを `transpose → contiguous → transpose` して非連続入力を作り、`not vt.is_contiguous()` をassertしていた。しかし、このfixtureのtail形状は **(1,2,1,128)**。長さ1の軸を転置して戻すと連続配置のままで、非連続化できていない。**僕が作ったテスト入力の構成不備であり、3方式の検査器による見逃しを観測した結果ではない。**

このassertは前hashの代入とpipeline呼出しより前にある。ここで止まると `before=None` のまま `input_unchanged=false` が付くため、このflagは今回、入力内容の実変化を示していない。元行は変更しない。ログ・元コード・NumPy上の配置確認 (`throughline/audits/loop-kv-vf01-results-v0.1-2026-10-02/noncontiguous-fixture-audit.json`)を照合した。CPUの配置確認は追加GPU試験ではない。

配布前の代役テストは `contiguous=False` を直接設定し、実際の非連続化手順を再現していなかった。この検査面の不足も誤判定標本台帳へ残した。原 `H1=false` を後から成功に書き換えない。
